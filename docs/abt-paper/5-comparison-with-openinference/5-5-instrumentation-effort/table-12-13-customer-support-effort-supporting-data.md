# Tables 12 and 13 Supporting Data: Customer Support Static Instrumentation-Effort Measurement

This document records the customer support agent data used in Tables 12 and 13.

## Measurement Target

| Variant | File |
|---|---|
| ABT | `src/experiments/customer_support_agent_abt/instrumented_agent.py` |
| Direct OI/Otel | `src/experiments/customer_support_agent_oi/instrumented_agent.py` |

The base customer support agent contains 1,453 non-empty, non-comment LOC.

## Measurement Definitions

| Metric | Definition |
|---|---|
| Instrumentation LOC | Non-empty, non-comment lines in the instrumentation adapter. |
| Instrumentation code ratio | Instrumentation LOC divided by base customer support agent LOC. |
| Instrumentation call-site count | Trace-related API or instrumentation-helper call sites in the instrumentation code. |
| Instrumentation API argument count | Explicit information items passed to instrumentation APIs, including top-level positional and keyword arguments and explicitly written nested trace fields. |

## Reproducibility Rule

The measurement is intended to be reproducible from the adapter source files. The same counting procedure must be applied to both variants.

1. Count only adapter code that exists to generate traces.
2. Exclude blank lines and comments from LOC.
3. Count one instrumentation point for each trace-related API or helper call site.
4. Count each explicit information item passed to an instrumentation API as one argument item.
5. For dictionary-based direct OI/Otel calls, count each explicitly written trace field inside the dictionary as an argument item.
6. Do not count business-logic statements that are shared with the base agent.

## Counting Note

The argument-count metric treats nested attribute dictionaries as multiple information items. For example, a direct OI/Otel call that passes a span name and an `attributes` dictionary with `openinference.span.kind`, `input.value`, `input.mime_type`, and `metadata` contributes multiple argument items because those trace fields are explicitly written by the developer. The values in this table are generated by the AST-based measurement script recorded in `table-12-13-automated-measurement-supporting-data.md`.

The customer support target is the only evaluated target where ABT has a higher instrumentation call-site count than direct OI/Otel. The AST breakdown shows that ABT uses separate behavior-level calls for behavior semantics, including `complete`, `input`, `decision`, and action-specific calls such as `target`, `provider`, `model_name`, `template`, `documents`, and `parameters`. This reflects the behavior shape of the customer support agent. Unlike the public-framework targets, which are dominated by repeated graph-node or execution-loop observations, the customer support agent intentionally exercises many heterogeneous Action types and subtype-specific fields. Therefore, the higher ABT call-site count reflects explicit recording of diverse behavior-level observations, while the lower ABT API argument count still reflects fewer manually supplied span-level trace fields.
